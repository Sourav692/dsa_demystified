Build and Serialize a Binary Tree

Turn a tree into a flat sequence and back again. Preorder hands you the roots in order; one extra piece of information (inorder positions, or explicit null markers) tells you where each subtree ends, and that pins the tree down uniquely.

Core idea: preorder gives roots, extra info gives the split Method 1: hash map + preorder pointer Method 2: preorder with null markers Interactive traces synced with code

Pattern README · Problems: Construct from Preorder + Inorder · Serialize and Deserialize

Canonical example

preorder = [3,9,20,15,7], inorder = [9,3,15,20,7]

Answer = tree [3,9,20,null,null,15,7]

Why this pattern matters

Saving and sending trees

A tree in memory is pointers. To write it to a file, cache it, or send it over a network, you need a flat string that can be turned back into the exact same shape.

Recovering structure from logs

Two traversal orders of the same tree are enough to rebuild it when values are distinct. That is the whole Construct problem.

Pattern reuse

The same "consume a sequence front to back, root first" recursion shows up in Construct, Serialize/Deserialize, and the related Encode and Decode Strings problem.

Instructor note: both problems answer one question: given a flat sequence, where does each subtree start and stop? Preorder answers "start" for free. The trick is always how you learn "stop".

What is the Build and Serialize pattern?

Simple definition

Preorder lists a tree as root, then left subtree, then right subtree. So the next unread preorder value is always the root of the subtree you are about to build. You rebuild recursively: take the root, build its left subtree, then its right subtree.

What you are actually building

A tree with a specific shape. Preorder alone cannot fix the shape, because it does not say where the left subtree ends. You add that information either from inorder positions (Construct) or from # markers for empty children (Serialize).

The tell: "construct / rebuild the tree from its traversals", "serialize and deserialize", "encode / decode", "save and restore a tree". One side is a flat list or string, the other side is a tree with a specific shape.

Step-by-step thinking process

1

Find the root

The next unread preorder value is the root of the current subtree. Keep one pointer (or iterator) that only moves forward.

2

Find where it splits

Construct: look the root up in the inorder index map. Serialize: the # markers end each subtree for you.

3

Recurse left, then right

Left first, always, because preorder lists the entire left subtree before the right one. The pointer then lands on the right subtree's root.

4

Stop on empty

An empty inorder window (lo > hi) or a # token means "no node here": return None.

How the inorder list becomes an index map

This is where beginners lose time. Before any recursion, turn inorder into a dictionary from value to position. Then "where does the root split the window?" is one lookup instead of a scan.

Input list

inorder = [9, 3, 15, 20, 7] index: 0 1 2 3 4
→

Index map idx

{9: 0, 3: 1, 15: 2, 20: 3, 7: 4}

enumerate(inorder) yields (0, 9), (1, 3), (2, 15), (3, 20), (4, 7)

The comprehension {v: i for i, v in enumerate(inorder)} flips each pair so the value is the key.

A subtree is a window inorder[lo..hi]

The whole tree is the window (0, 4). Its root is 3, and idx[3] = 1, so the left subtree is window (0, 0) and the right subtree is window (2, 4).

No slicing needed

The recursion passes two integers, not new lists. That is what turns the naive O(n²) build into O(n).

Critical point: the map only works because the values are distinct, which the problem guarantees. With duplicates, one value would have two positions.

Method 1: hash map + preorder pointer (Construct from Preorder and Inorder)

Precompute value to inorder index. Walk preorder with a single moving pointer. Each call owns an inorder window (lo, hi): it takes the next preorder value as its root, splits the window at that root, and builds left then right. This is the notebook's optimal Approach 2, line for line.

def build_fast(preorder: List[int], inorder: List[int]) -> Optional[TreeNode]: idx = {v: i for i, v in enumerate(inorder)} # value -> its position in inorder (O(1)) self_pre = [0] # our current position in preorder (in a list so it persists) def helper(lo, hi): # build the subtree covering inorder[lo..hi] if lo > hi: return None val = preorder[self_pre[0]] # next preorder value is this subtree's root self_pre[0] += 1 # advance the preorder pointer node = TreeNode(val) m = idx[val] # where the root splits inorder (instant lookup) node.left = helper(lo, m - 1) # build the left part first (preorder does left first) node.right = helper(m + 1, hi) # then the right part return node return helper(0, len(inorder) - 1)

Key mental model

The pointer reads preorder exactly once, left to right. Each call takes one value as its root; the window size decides how many values its subtree will consume before control returns.

Common mistake

Swapping lines 11 and 12. If the right subtree is built first, it grabs preorder values that belong to the left subtree and the tree comes out wrong.

Why the hash map matters

The naive version calls inorder.index(root) and slices both lists at every node: O(n²) time and space. The map plus bounds makes each node O(1), so the whole build is O(n).

Method 2: preorder with null markers (Serialize and Deserialize)

Here you design the sequence yourself. Write the tree in preorder and add a # for every empty child. Each # says "this subtree ends here", so no second traversal is needed. Deserialize reads the tokens back in the same order with the same recursion. Code is the notebook's optimal approach.

def serialize(root: Optional[TreeNode]) -> str: out = [] def dfs(n): # preorder walk, writing '#' for empty children if not n: out.append("#") # marker records where a child is missing return out.append(str(n.val)) # record this node's value dfs(n.left); dfs(n.right) # then its left subtree, then its right dfs(root) return ",".join(out) # e.g. "1,2,#,#,3,#,#" def deserialize(data: str) -> Optional[TreeNode]: vals = iter(data.split(",")) # read tokens in the SAME order serialize wrote them def build(): v = next(vals) if v == "#": # a '#' means "no node here" return None node = TreeNode(int(v)) node.left = build() # rebuild left subtree first (matches preorder) node.right = build() # then the right subtree return node return build()

Key mental model

Deserialize is serialize played back. The same recursion (root, left, right) runs in both directions, so token k is read by exactly the call that wrote it.

Common mistake

Leaving out the # markers. Without them "1,2" could mean 2 is the left child or the right child of 1: the shape is lost.

Why the iterator matters

iter(...) plus next(vals) is the same idea as Method 1's preorder pointer: a single shared cursor that only moves forward, so every token is read once and the whole round trip is O(n).

Edge cases you should test

Case A: empty tree

Construct: preorder = [], inorder = [] → helper(0, -1) returns None immediately.

Serialize: [] → "#", and deserialize reads that one # back as None.

Answer = None / "#"

Case B: single node

Serialize [1] → "1,#,#". Even a leaf writes two markers, one per empty child.

Answer = "1,#,#"

BFS level-order serialization (the notebook's Approach 1) produces the same string here.

Case C: two nodes

Construct: preorder = [1,2], inorder = [2,1]. Root 1 sits at inorder index 1, so the left window is (0,0) holding 2 and the right window (2,1) is empty.

Answer = 1 with left child 2

Preorder [1,2] alone could not tell left from right; the inorder position decides it.

Case D: negative values and a lopsided shape

Serialize [5,4,7,3,None,2,None,-1,None,9] → "5,4,3,-1,#,#,#,#,7,2,9,#,#,#,#".

Round trip reproduces the tree

Values are written with str and read with int, so -1 survives; the comma separator keeps multi-character tokens apart.

How to derive this in an interview

Reasoning path

Preorder's first value is the root, and after it come the whole left subtree, then the whole right subtree.

So I can rebuild recursively if I know where the left subtree ends.

Construct: inorder tells me, because the root splits it into left and right. A dict makes that split O(1).

Serialize: I control the format, so I write a # for each empty child and the markers tell me.

Either way one forward cursor plus left-before-right recursion gives O(n).

What to say out loud

  • "Preorder hands me roots in order; the question is where each subtree stops."
  • "I'll map each inorder value to its index so the split is O(1), and pass index bounds instead of slicing."
  • "I recurse left before right because preorder lists the left subtree first; the shared pointer depends on that."
  • "For serialize I write markers for empty children, so preorder alone is lossless, and I read tokens back in the same order."

Common beginner coding mistakes

Construct (Method 1) mistakes

  • Slicing preorder / inorder at each call: extra copies and easy off-by-one errors. Pass (lo, hi).
  • Calling inorder.index(root) inside the recursion, which brings back O(n²).
  • Building the right subtree before the left, so the pointer hands out the wrong roots.
  • Keeping the pointer in a plain local integer: the inner function cannot advance it. The notebook stores it in a one-element list.

Serialize (Method 2) mistakes

  • Omitting the markers for empty children, which makes the string ambiguous.
  • Reading tokens in a different order than they were written (for example BFS writer, DFS reader).
  • Joining values without a separator, so 1, -1 and 12 run together.
  • Forgetting the empty tree: it must serialize to something ("#") that deserializes back to None.

Practice questions

Commit to an answer before opening each one. Each links to that problem's step-through page.

Practice 1 — Construct: preorder = [1,2], inorder = [2,1]. Is 2 a left or right child?

Hint: find root 1 in inorder. What is on its left?

Answer: left child. idx[1] = 1, so the left window (0,0) holds 2 and the right window (2,1) is empty. Step through it: Construct Binary Tree from Preorder and Inorder.

Practice 2 — Construct: what goes wrong if you swap the two recursive calls in build_fast?

Hint: which value does the pointer hand out after the root?

Answer: on the canonical example the call helper(2, 4) would run first and read 9 (the next preorder value) as the root of the right subtree, but 9 belongs to the left subtree. Preorder lists left before right, so the recursion must too. See the step-through.

Practice 3 — Serialize: write [1,2,3,None,None,4,5] with BFS level order and null markers.

Hint: pop a node, write it, enqueue both children even when they are empty.

Answer: "1,2,3,#,#,4,5,#,#,#,#" (the notebook's Approach 1 prints exactly this). Preorder gives "1,2,#,#,3,4,#,#,5,#,#". Both have 11 tokens: 5 values and 6 markers. Open Serialize and Deserialize Binary Tree.

Practice 4 — Serialize: why can't you drop the # markers and send just "1,2"?

Hint: draw every tree whose preorder is 1, 2.

Answer: 2 could be the left child or the right child of 1; both trees have preorder 1, 2. With markers they differ: "1,2,#,#,#" versus "1,#,2,#,#". That is why Construct needs inorder and Serialize needs markers. See the step-through.

Final takeaway

Preorder tells you where each subtree starts; you only need one more fact to know where it stops. Construct gets that fact from inorder positions (via a hash map), Serialize builds it into the string as # markers. In both, one forward cursor and a left-before-right recursion rebuild the tree in O(n).
