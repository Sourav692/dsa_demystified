BFS Level Order

Walk a binary tree one level at a time with a queue. The single trick: freeze the queue's size at the start of each level, pop exactly that many nodes, and push their children. Each pass of the inner loop is then exactly one level of the tree.

Core idea: snapshot len(q) per level Method 1: Level Order Traversal Method 2: Right Side View Interactive traces synced to code

Problems in this pattern: Binary Tree Level Order Traversal · Binary Tree Right Side View · pattern notes (README)

Canonical example

Binary Tree Level Order Traversal, root = [3,9,20,null,null,15,7]

Answer = [[3], [9, 20], [15, 7]]

Why this pattern matters

Anything reported per level

Org charts by management layer, file trees by folder depth, game trees by move number: the output is grouped by distance from the top.

Shortest path when every step costs 1

BFS reaches nodes in order of distance from the start, so the first time it reaches a target is along a shortest path.

One template, many problems

Level Order Traversal and Right Side View share the same loop; only the line that records each level changes.

Instructor note: learn one loop shape, the level snapshot, and you can answer every "per level" tree question by changing a single line.

What is BFS level order?

Simple definition

Breadth-first search visits the tree row by row: the root, then all its children, then all their children. A queue (first in, first out) keeps nodes in the order they were found, so children always wait behind the rest of their parent's level.

The tell in a problem statement

The answer is organised per level: "level order", "row by row", "by depth", "visible from the right side", "rightmost node of each level", "average of each level", zigzag, minimum depth.

Beginner shortcut: at the moment a new level starts, the queue holds exactly that level. So len(q) right then is the level's size. Pop that many nodes and you have finished the level, no more and no less.

Step-by-step thinking process

1

Spot "per level"

The output has one entry per row of the tree. That points to BFS with a queue.

2

Seed the queue

Handle the empty tree, then start with q = deque([root]).

3

Drain one level

for _ in range(len(q)): pop a node, use it, push its left and right children.

4

Record the level

After the inner loop, append what this level contributes: its full list, or just its last node.

How the input becomes a tree and a queue

LeetCode gives the tree as a level-order list where null means "no child here". The notebook's build_tree turns that list into linked TreeNode objects, and it does so with the very same queue idea: each popped parent takes the next two list entries as its left and right child.

Input list

root = [3, 9, 20, null, null, 15, 7]
→

Linked nodes

3.left = 9 3.right = 20 9.left = None 9.right = None 20.left = 15 20.right = 7

Create the root 3

The first entry is the root. It goes into the builder's queue.

Pop 3, read 9, 20

They become 3's left and right children, and both join the queue.

Pop 9, read null, null

9 has no children; nothing joins the queue.

Pop 20, read 15, 7

They become 20's children. The list is used up, so the tree is complete.

Critical point: the BFS below works on the linked nodes, not on the list. Its queue holds TreeNode objects, and a node's children are reached through .left and .right, skipping any that are None.

Method 1: BFS level order (Binary Tree Level Order Traversal)

This is the template itself, taken line for line from the notebook's level_order_bfs. The queue starts with the root. Each outer pass snapshots len(q), pops that many nodes into a fresh level list, pushes their children, and appends the finished list.

def level_order_bfs(root: Optional[TreeNode]) -> List[List[int]]: res = [] if not root: return res q = deque([root]) while q: level = [] # values collected for the current level for _ in range(len(q)): # snapshot: current queue = exactly one level node = q.popleft() level.append(node.val) if node.left: q.append(node.left) # push the next level's nodes if node.right: q.append(node.right) res.append(level) # store this finished level return res

Key mental model

The queue is a conveyor belt. While level 1 is being popped from the front, level 2 is being loaded on the back. The frozen len(q) is the line painted between them.

Common mistake

Re-reading the queue length while children are being appended. At step 6 the queue grows to two new nodes; a moving bound would drag level 2 into level 1's list.

Why a deque

deque.popleft() is O(1). A Python list's pop(0) shifts every remaining element, O(n) per pop, which turns the whole traversal quadratic.

Method 2: keep only the last node per level (Binary Tree Right Side View)

Same loop, one line changed. Standing on the right, you see the rightmost node of each level. The inner loop pops a level left to right, so when it ends, node still points to the last node popped: the rightmost one. Append node.val instead of a whole list. Code from the notebook's right_side_view_bfs, traced on root = [1,2,3,null,5,null,4].

def right_side_view_bfs(root: Optional[TreeNode]) -> List[int]: res = [] if not root: return res q = deque([root]) while q: for _ in range(len(q)): # snapshot: current queue = exactly one level node = q.popleft() if node.left: q.append(node.left) # children wait in the queue for the next level if node.right: q.append(node.right) res.append(node.val) # `node` is the last one popped = rightmost on this level return res

Key mental model

Within one level the queue is ordered left to right, so "last popped" means "rightmost". Node 5 is popped before 4 on level 2, which is exactly why 5 is hidden.

Common mistake

Walking only the right spine (root.right.right...). On [1,2,3,4,null,null,null,5] the answer is [1, 3, 4, 5]: levels 2 and 3 exist only on the left.

Why the template still fits

The level boundary is what lets you say "last of this level". Without the len(q) snapshot there is no way to know which pop ends a level.

Edge cases you should test

Case A: empty tree

root = []

Level order = [] · Right side view = []

The if not root: return res guard runs before the queue is built. Without it, deque([None]) would pop None and crash on .val.

Case B: single node

root = [1]

Level order = [[1]]

One outer pass with len(q) = 1; no children are pushed, so the loop ends.

Case C: every node is a left child

root = [1, 2, null, 3, null, 4]

Right side view = [1, 2, 3, 4]

Each level has a single node, so it is both the leftmost and the rightmost: every node is visible.

Case D: the right subtree is shorter

root = [1, 2, 3, 4, null, null, null, 5]

Right side view = [1, 3, 4, 5]

Levels 2 and 3 contain only left-subtree nodes, so 4 and 5 are visible from the right.

How to derive this in an interview

Reasoning path

The answer has one entry per level of the tree.

A queue hands out nodes in level order, because children always join the back.

To know where one level ends, freeze len(q) when the level starts and pop exactly that many.

Decide what each level records: the whole list, or only the last node popped.

What to say out loud

  • "The output is grouped by level, so I'll use BFS with a deque."
  • "At the start of each level, the queue holds exactly that level, so I snapshot len(q) and pop that many nodes."
  • "For the right side view, the last node popped in each level is the rightmost, so I append it after the inner loop."
  • "Every node is pushed and popped once: O(n) time; the queue holds about one level: O(w) space."

Common beginner coding mistakes

Level Order Traversal

  • Reading the queue length after children were appended, so levels blur together.
  • Creating level = [] outside the while loop, so every level shares one list.
  • Using list.pop(0) instead of deque.popleft(): O(n) per pop.
  • Forgetting the empty-tree guard.

Right Side View

  • Following only the right spine and missing deeper left-subtree nodes.
  • Recording the first node popped per level: that is the left side view.
  • In the DFS version, exploring left before right, so the first node per depth is the leftmost.
  • Appending node.val inside the inner loop instead of after it.

Answer: [1, 3, 4, 5]. Levels 2 and 3 have only left-subtree nodes, so they are the rightmost on their levels. See the problem demo on the Right Side View page.

Practice 4 — Why does Right Side View's brute force slow down about 4x per doubling on a chain?

Hint: how many depths does a chain of n nodes have, and what does each pass rescan?

Answer: a chain has h = n levels and the pass for depth d rewalks every node above it, so the total is about n²/2 visits: O(n·h) = O(n²). BFS visits each node once. Walkthrough: Binary Tree Right Side View.

Final takeaway

Freeze len(q), drain exactly that many, push the children. That one loop turns a queue into a level-by-level walk. Level Order Traversal records each level's full list; Right Side View records only the last node popped. Same template, one line apart.
