BST Property

A binary search tree keeps one promise at every node: everything on the left is smaller, everything on the right is larger. This lesson shows how that single promise turns three Medium problems into short loops: walk toward an answer by comparison, carry a (low, high) window down a DFS, and read values in sorted order with an in-order walk.

Core idea: let the ordering choose the branch Interactive LCA walk Interactive (low, high) bounds trace Code synced with steps

Problems in this pattern: Lowest Common Ancestor of a BST · Validate Binary Search Tree · Kth Smallest Element in a BST

Canonical example: LCA of a BST

tree = [6,2,8,0,4,7,9], p = 0, q = 4

Answer = 2 (2 nodes visited, right subtree never touched)

Why this pattern matters

Ordered lookups

Sorted maps and database indexes are search trees for the same reason: one comparison per level discards a whole branch, so a lookup costs the height, not the size.

Range checks

Asking "does every value in this subtree fit between two limits?" is the same window idea Validate BST uses, and it is how range queries skip subtrees.

Pattern reuse

Three NeetCode 150 problems fall to it: Lowest Common Ancestor of a BST, Validate Binary Search Tree, and Kth Smallest Element in a BST.

Instructor note: the word BST in a problem statement is a hint, not decoration. If your solution would work just as well on an unordered binary tree, you are probably not using the information you were given.

What is the BST property?

Simple definition

For every node, all values in its left subtree are smaller than it and all values in its right subtree are larger. Not just the children: the whole subtree. That makes every node live inside a window set by all of its ancestors.

What you get from it

Three moves. Walk by comparison: one test tells you which side can hold a value. Carry bounds: going left caps the window at the node, going right raises its floor. In-order is sorted: left, node, right visits values smallest first.

Beginner shortcut (the tell): "in a BST" plus "ancestor / split" means walk by comparison; "is it a valid BST" means carry (low, high); "k-th smallest" or "sorted order" means in-order with a counter.

Step-by-step thinking process

1

Spot the BST

Check the statement says binary search tree. Without the ordering, none of these shortcuts are valid.

2

Ask what the order buys you

A direction to walk (LCA), a window each node must fit (validation), or a sorted visiting order (k-th smallest).

3

Pick the move

Comparison walk is O(h). Bounds DFS touches every node, O(n). In-order with early stop is O(h + k).

4

Handle the boundaries

Equal values (a target equal to the node is the LCA), strict < for validity, and 1-indexed k.

How the input becomes a BST (and a window per node)

LeetCode gives the tree as a level-order list. The notebooks' build_tree attaches children left to right, level by level, with None for a missing child. Once the tree exists, each node also has an implied window from its ancestors.

Input list

tree = [6, 2, 8, 0, 4, 7, 9]
→

Tree and the window each node lives in

6 window (-inf, +inf) ├─ 2 window (-inf, 6) │ ├─ 0 window (-inf, 2) │ └─ 4 window (2, 6) └─ 8 window (6, +inf) ├─ 7 window (6, 8) └─ 9 window (8, +inf)

Take 6 as the root

Nothing above it, so its window is (-inf, +inf).

Attach 2 left and 8 right of 6

Going left caps the window at 6: 2 must be in (-inf, 6). Going right raises the floor to 6: 8 must be in (6, +inf).

Attach 0, 4 under 2, then 7, 9 under 8

4 is right of 2 but still left of 6, so its window is (2, 6): it inherits the cap from its grandparent.

Read it in-order

Left, node, right gives 0 2 4 6 7 8 9: sorted. That is the fact Kth Smallest uses.

Critical point: a node's window comes from all its ancestors, not only its parent. 4 is checked against 2 (parent) and 6 (grandparent). Forgetting the grandparent is the classic Validate BST bug.

Method 1: Walk by comparison (Lowest Common Ancestor of a BST)

Start at the root. If both targets are smaller than the node, the answer can only be on the left; if both are larger, only on the right. The first node where that is not true is where the two paths split, and that node is the lowest common ancestor. This is the notebook's optimal lca_iter, unchanged.

def lca_iter(root: Optional[TreeNode], p: int, q: int) -> int: node = root while node: if p < node.val and q < node.val: # both targets are smaller -> go left node = node.left elif p > node.val and q > node.val:# both targets are larger -> go right node = node.right else: # they split here (one each side, or equal) return node.val # this is the lowest common ancestor return -1

Key mental model

While both targets are on the same side, the ancestor they share is further down that side. The moment they are not, you are standing on the split point.

Common mistake

Searching both subtrees like the plain binary-tree LCA. It still works, but it is O(n) and ignores the ordering you were given.

Why no stack is needed

The walk never backtracks: each step goes to exactly one child. That is why the iterative version uses O(1) extra space while the recursive one uses O(h).

Method 2: Carry a (low, high) window (Validate Binary Search Tree)

The same ordering, used the other way round: instead of choosing a direction, check that each node fits the window its ancestors allow. Going left, the node's value becomes the new upper bound; going right, it becomes the new lower bound. This is the notebook's is_valid_bounds, traced on its trickiest test, [5,4,6,None,None,3,7].

def is_valid_bounds(root: Optional[TreeNode]) -> bool: def valid(node, low, high): # node's value must stay strictly inside (low, high) if not node: return True # empty subtree is fine if not (low < node.val < high): # out of its allowed range -> not a BST return False # Going left tightens the upper bound; going right tightens the lower bound. return valid(node.left, low, node.val) and valid(node.right, node.val, high) return valid(root, float("-inf"), float("inf"))

Key mental model

The window only ever shrinks on the way down. A node inherits its parent's window and then cuts one side at the parent's value.

Common mistake

Checking only left.val < node.val < right.val. Node 3 is a perfectly good left child of 6, yet the tree is invalid because 3 sits on the right of 5.

Same property, read in order

The notebook's second approach walks in-order and fails when a value is not strictly greater than the previous one: here it sees 4, 5, 3 and stops. That in-order walk with a counter is exactly Kth Smallest.

Edge cases you should test

Case A: one target is an ancestor of the other

tree = [6,2,8,0,4,7,9], p = 2, q = 4

Answer = 2

At 6 both are smaller, so go left. At 2, p < 2 is false because p == 2, so neither branch test holds and the else returns 2. A node counts as its own ancestor.

Case B: the targets split at the root

tree = [6,2,8,0,4,7,9], p = 2, q = 8

Answer = 6

One target is smaller than 6 and one is larger, so the very first comparison lands in else. One node visited.

Case C: a right child smaller than its parent

[5,1,4,None,None,3,6]

Answer = False

valid(4, 5, inf) fails straight away: 4 is the right child of 5 but is not greater than 5. Here even a parent-only check would catch it; Method 2's tree is the case only the window catches.

Case D: a single node

[1]: valid BST, and with k = 1 the k-th smallest is 1

Valid = True · kth(1) = 1

Both children are None, which return True. In-order visits 1 first, so count == 1 == k on the first pop.

How to derive this in an interview

Reasoning path

The input is a BST, so at every node I know which side any value would be on.

For LCA: while both targets are on the same side, the shared ancestor is further down that side. Walk until they split.

For validation: "left subtree smaller" means the whole subtree, so a node must respect every ancestor. Pass the allowed window down.

For k-th smallest: in-order visits a BST in sorted order, so count visits and stop at k.

What to say out loud

  • "It's a BST, so one comparison tells me which subtree can hold the answer."
  • "For LCA I walk down until p and q stop being on the same side; that's O(h) time and O(1) space."
  • "Comparing a node to its parent isn't enough; I'll carry a (low, high) window, strict on both ends."
  • "In-order is sorted, so the k-th smallest is the k-th node I pop; I stop early for O(h + k)."

Common beginner coding mistakes

Comparison walk (LCA)

  • Searching both subtrees as in the general binary-tree LCA, which is O(n).
  • Forgetting that a target equal to the node makes that node the answer (the else branch).
  • Using this walk when the tree is not a BST: the comparisons then mean nothing.

Bounds and in-order (Validate, Kth Smallest)

  • Comparing a node only with its direct children, which misses grandparent violations.
  • Using <= where the notebooks use strict <; duplicates are not allowed.
  • Treating k as 0-indexed: the answer is vals[k - 1], or the node where count == k.
  • Building the whole in-order list when stopping at the k-th value would do.

Final takeaway

A BST answers one question at every node for free: which side would this value be on? Use it to walk (LCA, O(h)), to bound (validation, a shrinking (low, high) window), or to sort (in-order with a counter for the k-th smallest). If your solution ignores the ordering, you are solving the harder plain-tree problem.
