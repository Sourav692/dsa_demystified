Heap Simulation

Some problems do not ask you to find something clever. They describe a process ("each turn, take the two heaviest...") and ask what is left at the end. Run that process literally, and keep the items in a max-heap so that every "which one is biggest right now?" costs O(log n) instead of a full sort.

Core idea: pop the best, act, push back what is left Method 1: Last Stone Weight Method 2: Task Scheduler (cooldown queue) Interactive traces synced to code

Problems in this pattern: Last Stone Weight · Task Scheduler · pattern notes (README)

Canonical example

Last Stone Weight, stones = [2,7,4,1,8,1]. After heapify, the heaviest stone sits at the top of the tree.

Answer = 1

Why this pattern matters

Schedulers and job queues

An operating system or a print queue always runs the most urgent job next, while new jobs keep arriving and finished jobs come back with lower priority.

Event-driven simulations

Games, traffic models and bank-queue simulations repeatedly process "the next thing to happen", and each event can create new ones.

One loop, two problems

Last Stone Weight and Task Scheduler share the same loop: pop the best, apply the rule, push back what is left. Task Scheduler adds one queue for items that must wait.

Instructor note: when a statement says "each turn, take the largest", do not look for a formula first. Simulate it, and ask only one question: how do I get the largest item fast, every turn, while the collection keeps changing? The answer is a heap.

What is heap simulation?

Simple definition

A simulation follows the rules of the statement step by step. A max-heap is a list arranged as a tree where every parent is at least as big as its children, so the biggest item is always at position 0. Popping it or pushing a new item moves one item along one path of the tree: O(log n). Python's heapq is a min-heap, so we store values negated.

The tell in a problem statement

A process ("each turn", "repeatedly", "until one is left", "each interval"), every step needs the current largest item, and the collection changes after each step: a smaller leftover goes back in. Twist: a used item may have to wait before it can return ("cooldown", "at least n apart").

Beginner shortcut: sorting once does not survive the first step, because the leftover can belong anywhere in the order. A heap does not keep the whole list sorted; it only guarantees the top. That is all the process needs, and it is much cheaper to maintain.

Step-by-step thinking process

1

Spot the process

The answer is "whatever the repeated rule leaves behind", and each step needs the biggest item.

2

Build the heap

Negate the values and heapify once: O(n). For tasks, the values are the counts.

3

Pop, act, push back

Pop the best, apply one step of the rule, and push back whatever is left of it.

4

Make it wait if needed

If the leftover may not return yet, park it in a queue with its release time; push it back when that time comes.

How the input becomes a max-heap

The notebook's last_stone_weight_heap turns the plain list of weights into a heap in two lines. The heap is still a Python list; only the order of its items changes, so that position i is the parent of positions 2i+1 and 2i+2.

Input list

stones = [2, 7, 4, 1, 8, 1]
→

Heap list (stored negated)

heap = [-8, -7, -4, -1, -2, -1] real = [ 8, 7, 4, 1, 2, 1]

Negate every weight

[-2, -7, -4, -1, -8, -1]. Now the heaviest stone is the smallest number, which is what a min-heap puts on top.

heapq.heapify(heap)

Rearranges the list in place in O(n) so every parent is at most its children (in negated terms). Result: [-8, -7, -4, -1, -2, -1].

Read it as a tree

Position 0 (8) is the root; positions 1 and 2 (7, 4) are its children; positions 3, 4 (1, 2) hang under 7 and position 5 (1) under 4.

Only the top is guaranteed

The list is not sorted (2 sits after 1), and it does not need to be: each round only asks for the top, twice.

Critical point: every value going into the heap is negated (-s, -(y - x)) and every value coming out is negated back (-heapq.heappop(heap)). Miss one side and the heap silently orders stones lightest-first.

Method 1: max-heap simulation (Last Stone Weight)

The template in its simplest form, line for line from the notebook's last_stone_weight_heap. Each round pops the two heaviest stones; if they differ, the leftover y - x is pushed back and competes in later rounds. The loop stops when at most one stone is left.

def last_stone_weight_heap(stones: List[int]) -> int: heap = [-s for s in stones] # negate: heapq is a min-heap, we need the max heapq.heapify(heap) # O(n) build; heap[0] = -(heaviest) while len(heap) > 1: y = -heapq.heappop(heap) # heaviest x = -heapq.heappop(heap) # second heaviest if y != x: heapq.heappush(heap, -(y - x)) # leftover goes back in: it may be the max later return -heap[0] if heap else 0

Key mental model

The heap is a "biggest-first" waiting room. Each round two stones leave from the front door, and the leftover walks back in and finds its own seat: at step 7 the new 2 goes straight to the top, at step 4 the new 1 stays at the bottom.

Common mistake

Sorting once at the start. After round 1 the leftover 1 belongs at the bottom, but after round 2 the leftover 2 is the heaviest stone. Only a structure that re-finds the top every round gets both right.

Why a heap

Re-sorting the pile every round also works (the notebook's brute force), but it redoes a whole sort per round. The heap does two pops and one push per round, O(log n) each: O(n log n) in total.

Method 2: max-heap plus a cooldown queue (Task Scheduler)

Same loop, one twist: a task type that just ran may not run again for n ticks, so instead of going straight back into the heap it waits in a FIFO queue as (copies left, release time). The heap holds only counts; the letters do not matter. Code from the notebook's least_interval_heap, traced on tasks = [A, A, A, B, C], n = 3 (answer 9), an example where the clock has to jump over idle ticks.

def least_interval_heap(tasks: List[Hashable], n: int) -> int: heap = [-c for c in Counter(tasks).values()] # max-heap of copies left (negated) heapq.heapify(heap) cooldown = deque() # (negated copies left, tick it is released) time = 0 while heap or cooldown: time += 1 if heap: cnt = heapq.heappop(heap) + 1 # run one copy of the biggest pile (+1 because negated) if cnt: # copies remain: park it for n ticks cooldown.append((cnt, time + n)) else: time = cooldown[0][1] # nothing runnable: idle until the front is released if cooldown and cooldown[0][1] == time: # front's cooldown ends this tick heapq.heappush(heap, cooldown.popleft()[0]) return time

Key mental model

Two waiting areas. The heap holds piles that may run now, biggest first. The cooldown queue holds piles that must wait, in the order they ran, and since every wait is the same n ticks, the front is always the next one out.

Common mistake

Pushing the pile straight back into the heap after it runs. At step 1 the 2 would be popped again at time 2, running A twice in a row and returning a too-small answer.

Why the jump

At step 6 nothing can run until time 8. Setting time = cooldown[0][1] skips ticks 6 to 8 in one loop pass, so the loop runs once per task or idle stretch, not once per tick: O(T log k).

Edge cases you should test

Case A: one stone

stones = [1]

Last Stone Weight = 1

len(heap) = 1, so the while loop never runs and -heap[0] is returned.

Case B: everything cancels

stones = [2, 2] and stones = [1, 1, 1, 1]

Last Stone Weight = 0

Equal stones push nothing back, so the heap can end empty. The if heap else 0 guard is what returns 0 instead of crashing on heap[0].

Case C: cooldown of zero

tasks = [A, A, A, B, B, B], n = 0

Task Scheduler = 6

A parked pile is released at time + 0, the same tick, so it rejoins the heap at once and no tick is idle: the answer is len(tasks).

Case D: other tasks fill every gap

tasks = [A, C, A, B, D, B], n = 1

Task Scheduler = 6

There is always another pile to run while one cools down, so no idle is needed. In the formula, (2 - 1) * (1 + 1) + 2 = 4 is smaller than len(tasks) = 6, which is why the formula takes the max.

How to derive this in an interview

Reasoning path

The statement describes a repeated process; the answer is what it leaves behind.

Every step needs the current largest item, and the collection changes after every step.

Re-sorting each step works but repeats work; a max-heap gives the top in O(log n).

If a used item must wait, park it in a queue with its release time and push it back when the time comes.

What to say out loud

  • "Each turn needs the two heaviest stones of the current pile, so I'll keep the pile in a max-heap, using heapq with negated values."
  • "Pop twice, push the difference back if it is non-zero; stop at one stone. That is O(n log n)."
  • "For the scheduler, only counts matter. Greedily run the biggest pile; a pile that just ran waits in a queue with its release time."
  • "When the heap is empty I jump the clock to the next release, so the loop is O(T log k). If they only want the length, the frame formula gives it in O(T)."

Common beginner coding mistakes

Last Stone Weight

  • Negating on the way out but not on the way in (or the reverse), so the leftover lands in the wrong place.
  • Sorting once and assuming the order holds after the first smash.
  • Returning heap[0] (a negative number) instead of -heap[0].
  • Crashing on an empty heap when the last two stones were equal.

Task Scheduler

  • Pushing a pile straight back into the heap, ignoring the cooldown.
  • Parking a pile with 0 copies left, which then comes back and runs a task that does not exist.
  • Ticking through idle time one tick at a time instead of jumping time.
  • In the formula, forgetting count_max or the max(len(tasks), ...).

Practice 1 — Last Stone Weight: stones = [3, 3, 3]

Hint: what happens when the two heaviest are equal?

Answer: 3. The first two 3s destroy each other and push nothing back; one stone is left. Step through the smashes on Last Stone Weight.

Practice 2 — Task Scheduler: tasks = [A, A, A, B, B, B], n = 3

Hint: two full frames of n + 1 = 4 ticks, then the last frame.

Answer: 10: A B idle idle A B idle idle A B, which is (3 - 1) * 4 + 2. Compare the three solutions on Task Scheduler.

Practice 3 (variant of Task Scheduler) — Reorganize String (LeetCode 767): rearrange "aab" so no two neighbours are equal

Hint: it is Task Scheduler with n = 1, but you must output the order, and idling is not allowed. Pop the biggest pile, append its letter, and hold that pile back for exactly one step before pushing it again.

Answer: "aba". If the heap is empty while a pile is still held back, no valid order exists (e.g. "aaab"): return "". The formula cannot do this, which is why the heap simulation is the template. Review the cooldown queue on Task Scheduler.

Practice 4 (variant of Last Stone Weight) — what changes if each turn smashes the two lightest stones?

Hint: which kind of heap gives the smallest item directly?

Answer: use heapq as is, a min-heap, with no negation; the loop body stays the same shape (pop two, push the leftover). The same min-heap loop solves "Minimum Cost to Connect Sticks" (pop the two shortest, push their sum). Compare with the max-heap version on Last Stone Weight.

Final takeaway

Pop the best, apply the rule, push back what is left. A max-heap turns "simulate the process" into O(log n) per step. Last Stone Weight is the loop as is; Task Scheduler adds a cooldown queue so a used item waits before it competes again.
