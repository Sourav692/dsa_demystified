Fixed Window

Slide a window of exactly k elements along an array or string. Each step, one element enters on the right and the element at r - k leaves on the left. Keep a small summary of the window (letter counts, a sum, a line of candidate maximums) and update it with those two elements instead of rebuilding it for every window.

Core idea: one in, one out, size stays k Method 1: Permutation in String Method 2: Sliding Window Maximum Interactive traces synced to code

Problems in this pattern: Permutation in String · Sliding Window Maximum · pattern notes (README) · look-alike: Variable Window

Canonical example

Permutation in String, s1 = "ab", s2 = "eidbaooo", window size k = len(s1) = 2

Answer = True ("ba" at indices 3..4)

Why this pattern matters

Rolling metrics

"Average of the last 7 days", "requests in the last 60 seconds": a dashboard slides a fixed window over a stream and updates the total as one reading arrives and one expires.

Peak over a recent period

The highest load or price over the last k ticks is exactly Sliding Window Maximum. A deque of candidates answers it without rescanning the whole period every tick.

Fingerprinting blocks of text

Finding scrambled copies of a word, or every block of k letters with a given makeup, is a fixed window of letter counts sliding over the text.

Instructor note: the whole pattern is "neighbouring windows share k - 1 elements". Once you see that, the only real question in each problem is: what summary of the window can I update with one element in and one element out?

What is a fixed sliding window?

Simple definition

A window is a contiguous slice arr[l..r]. A fixed window always holds exactly k elements. It moves one step at a time: index r enters on the right, index r - k leaves on the left, and once r >= k - 1 the slice arr[r-k+1..r] is a full window to check or record.

The tell in a problem statement

The length is given or implied and never changes: "subarray of length k", "window of size k", "a permutation / anagram of p inside s" (length len(p)), "maximum / average of each window". If you are asked for the longest or shortest window, the size is the unknown: that is a variable window.

Beginner shortcut: write one for r loop with three lines in it: add arr[r]; if r >= k, remove arr[r - k]; if r >= k - 1, record. Every fixed-window problem fills in those three lines.

Step-by-step thinking process

1

Spot the fixed size

Every candidate has the same length k. Brute force would look at each of the n - k + 1 windows from scratch: O(n·k).

2

Pick the summary

What do you need to know about a window? Letter counts (permutation), a sum (average), the max (a monotonic deque).

3

One in, one out

Update the summary with arr[r] entering and arr[r - k] leaving. The update must be O(1), or amortised O(1).

4

Record when full

From r = k - 1 on, every step completes a window: compare it, or append its answer.

How the input becomes a window summary

For Permutation in String the summary is two arrays of 26 numbers. Letter c lives in slot ord(c) - ord('a'): a is slot 0, b slot 1, and so on. need is built once from s1; window changes by exactly two slots per step.

Input strings

s1 = "ab" k = len(s1) = 2 s2 = "eidbaooo" n = len(s2) = 8
→

Count arrays (non-zero slots)

need = {a:1, b:1} slots 0 and 1 window = {} starts empty, then +1 for s2[r], -1 for s2[r-k]

Build need from s1

a adds 1 to slot 0, b adds 1 to slot 1. This never changes again.

Fill the first window: r = 0, 1

e then i enter. Nothing leaves yet, because r < k. At r = 1 the window holds 2 letters: it is full.

Slide: r = 2, 3, ...

Each step one slot goes up (the letter entering) and one goes down (the letter at r - 2 leaving). The window's letter total stays at 2.

Compare

window == need compares 26 slots: a fixed cost, so it counts as O(1). Equal counts mean the window is a rearrangement of s1.

Critical point: for Sliding Window Maximum the summary is not a count but a deque of indices. A count can be decremented when an element leaves; a maximum can't. Method 2 shows the structure that replaces it.

Method 1: fixed window of letter counts (Permutation in String)

The template with counts as the summary, taken line for line from the notebook's check_inclusion_window. Line 8 is "add", line 10 is "remove", line 11 is "record when full".

def check_inclusion_window(s1: str, s2: str) -> bool: k = len(s1) need = [0] * 26 # letter counts of s1 (the target) for c in s1: need[ord(c) - ord('a')] += 1 window = [0] * 26 # letter counts of the current window of s2 for r in range(len(s2)): window[ord(s2[r]) - ord('a')] += 1 # 1) s2[r] enters on the right if r >= k: window[ord(s2[r - k]) - ord('a')] -= 1 # 2) s2[r-k] leaves on the left: size stays k if r >= k - 1 and window == need: # 3) full window with s1's counts = permutation return True return False # also covers k > len(s2): never full

Key mental model

The window is a caterpillar: the head steps onto s2[r], the tail lifts off s2[r - k], and the body length never changes. Only two count slots move per step.

Common mistake

Removing s2[r - k + 1] instead of s2[r - k]. At step 3 the letter leaving is e (index 0); index 1 (i) is still inside the window "id".

Why counts, not sorting

Sorting also ignores order, but it has to be redone for every window: O(k log k) each. Counts are updated with +1 / -1. The notebook measures the sort version at about 4x per doubling and this one at about 2x.

Method 2: fixed window with a monotonic deque (Sliding Window Maximum)

Same loop, but the summary is a deque of indices whose values decrease from front to back, so nums[q[0]] is always the window's max. "Add" first throws away every older value the newcomer beats (lines 5-6): they can never be a maximum again. "Remove" pops the front only if its index is r - k (lines 8-9). Code from the notebook's max_sliding_window_deque, traced on nums = [5, 4, 3, 2, 6, 1], k = 3, an input where both kinds of pop happen.

def max_sliding_window_deque(nums: List[int], k: int) -> List[int]: q = deque() # indices; nums[q[0]] > nums[q[1]] > ... (decreasing) res = [] for r, x in enumerate(nums): while q and nums[q[-1]] <= x: # 1) x enters: drop older values it beats, q.pop() # they can never be a window max again q.append(r) if q[0] == r - k: # 2) index r-k leaves: pop it if it is the front q.popleft() if r >= k - 1: # 3) window [r-k+1, r] is full: front is its max res.append(nums[q[0]]) return res

Key mental model

A line of candidates for "tallest in the room", ordered tallest first. A newcomer who is at least as tall as the people at the back sends them home: they will leave the room earlier and never be tallest again.

Common mistake

Storing values instead of indices. At step 4 the deque must know that its front 5 sits at index 0 = r - k; a bare 5 can't say whether it is still inside the window.

Why it is still O(n)

Step 5 pops three items at once, but each index is appended once and popped at most once over the whole run. Total work is O(n); the notebook measures about 2x per doubling.

Edge cases you should test

Case A: len(s1) > len(s2)

s1 = "abc", s2 = "ab"

Permutation in String = False

No window of width 3 fits in 2 letters. r >= k - 1 is never true, so the loop ends and returns False without a special guard.

Case B: one window covers everything

nums = [2, 7, 1, 8], k = 4; and s1 = "a", s2 = "a"

[8] · True

The window becomes full at the last index and nothing ever leaves.

Case C: window of one

nums = [1, 2, 3, 4], k = 1

Sliding Window Maximum = [1, 2, 3, 4]

Every number is its own window. Each step the previous index (r - 1) leaves, so every step ends with a single index in the deque.

Case D: right letters, wrong amounts

s1 = "aab", s2 = "abbba"

Permutation in String = False

Every window uses only a and b, but none has two as. Comparing the set of letters would wrongly say True.

Case E: equal values

nums = [4, 4, 4, 1], k = 2

Sliding Window Maximum = [4, 4, 4]

With <= the newer 4 replaces the older one, which would leave the window first anyway. The deque stays strictly decreasing.

How to derive this in an interview

Reasoning path

Every candidate has the same length k, so brute force is "check each of the n - k + 1 windows": O(n·k).

Neighbouring windows share k - 1 elements. Only arr[r] enters and arr[r - k] leaves.

Choose a summary that updates in O(1): counts for "same letters", a sum for averages.

If the summary is a max or min, it can't be undone: keep a decreasing deque of indices instead.

What to say out loud

  • "Every candidate is exactly len(s1) long, so I'll slide a fixed window over s2."
  • "Two strings are permutations when their letter counts match, so the window keeps 26 counts: +1 for the letter entering, -1 for the letter at r - k leaving."
  • "For the maximum I can't subtract, so I keep indices with decreasing values in a deque. The front is the max; each index is pushed and popped once, so it's O(n)."
  • "I only record once r >= k - 1, when the window is full."

Common beginner coding mistakes

Permutation in String

  • Removing s2[r - k + 1]: that letter is still inside the window.
  • Comparing before the window is full, or forgetting to compare the very first full window.
  • Comparing the set of letters instead of their counts.
  • Recounting each window with Counter(s2[l:l+k]): correct, but O(n·k).

Sliding Window Maximum

  • Storing values, not indices, so the front's age is unknown.
  • Flipping the comparison to >=: the deque becomes increasing and returns minimums.
  • Evicting from the back instead of the front when an index leaves the window.
  • Calling it O(n·k) because of the inner while: count pops over the whole run.

Practice 1 — Permutation in String: s1 = "adc", s2 = "dcda"

Hint: the windows of width 3 are "dcd" and "cda".

Answer: True, at r = 3: the window "cda" has counts {a:1, c:1, d:1}, the same as "adc". Step through the method on Permutation in String.

Practice 2 — Sliding Window Maximum on [1, 3, -1, -3, 5, 3, 6, 7], k = 3: does the front-eviction line (q[0] == r - k) ever fire?

Hint: look at what happens to each old maximum before it gets k steps old.

Answer: never. Every old front is thrown off the back by a bigger-or-equal newcomer first (3 by 5 at r = 4, 5 by 6, 6 by 7). The answer is [3, 3, 5, 5, 6, 7]. The eviction matters on decreasing runs, like [5, 4, 3, 2, ...]. Compare on Sliding Window Maximum.

Practice 3 (follow-up variant of Permutation in String) — Find every start index of an anagram of p = "abc" in s = "cbaebabacd"

Hint: same loop; instead of return True, record the window's start r - k + 1 and keep going.

Answer: [0, 6] ("cba" and "bac"). This is LeetCode "Find All Anagrams in a String". The template change is one line; see the base problem on Permutation in String.

Practice 4 (follow-up variant of Sliding Window Maximum) — Window minimum of [5, 4, 3, 2, 6, 1], k = 3

Hint: keep the deque increasing: pop from the back while nums[q[-1]] >= x.

Answer: [3, 2, 2, 1]. Everything else (indices, front eviction at r - k, recording when full) is unchanged. Base walkthrough: Sliding Window Maximum.

Final takeaway

Add arr[r], remove arr[r - k], record once r >= k - 1. That loop is the whole pattern. Permutation in String keeps 26 letter counts in it; Sliding Window Maximum keeps a decreasing deque of indices, because a maximum can't be subtracted. Both visit each element a constant number of times: O(n).
