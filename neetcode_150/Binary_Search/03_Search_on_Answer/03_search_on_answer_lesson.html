Search on Answer

Some problems ask for the smallest value you get to choose (a speed, a capacity, a number of days) that still meets a limit. You cannot search the input for it, but you can search the range of possible answers. If one guess can be checked quickly and the check is monotonic, binary search finds the smallest value that passes.

Core idea: binary search a yes/no check over the answers Method 1: Binary search the speed Method 2: Try every speed (brute force) Interactive traces synced to code

Problem in this pattern: Koko Eating Bananas · pattern notes (README)

Canonical example

Koko Eating Bananas, piles = [3, 6, 7, 11], h = 8: the slowest eating speed that finishes in 8 hours.

Answer = 4

Why this pattern matters

Capacity planning

"What is the smallest machine, truck or bandwidth that still meets the deadline?" Checking one size is a quick simulation; trying every size is not.

Fair splitting of work

"Split these jobs into m consecutive batches so the biggest batch is as small as possible." Guess the biggest allowed batch, then check whether m batches are enough.

Huge answer ranges

When the answer can be anywhere up to 10^9, a linear scan is hopeless, but about 30 halvings reach any value in that range.

Instructor note: the hard part is not the binary search, it is noticing that you can binary search. The input array is usually unsorted. What is sorted is the line of yes/no answers to "does this guess work?"

What is search on answer?

Simple definition

Pick a range [lo, hi] that surely contains the answer. Write feasible(x), a yes/no check for one guess. If the check is monotonic (once a guess works, every bigger guess works too), the answers read no ... no YES ... YES, and binary search finds the first YES.

The tell in a problem statement

"Minimum speed / capacity / days such that ... within h hours / D days", "minimize the maximum", "maximize the minimum", and a value range far bigger than n (up to 10^9).

Beginner shortcut: ask "if I were told the answer, could I check it in one pass?" and "if x works, does x + 1 work?" Two yeses mean binary search on the answer.

Step-by-step thinking process

1

Name the answer

What number do you choose? For Koko: the eating speed k.

2

Write the check

feasible(k): total hours sum((p + k - 1) // k) is at most h. One O(n) pass.

3

Confirm monotonic, set bounds

Faster never takes longer, so it is monotonic. lo = 1 (slowest), hi = max(piles) (always fits).

4

Find the first YES

While lo < hi: feasible mid means hi = mid; otherwise lo = mid + 1. Return lo.

How the input becomes a yes/no line

The piles are never sorted or searched. They are only read inside the check. What the binary search walks over is a line of candidate speeds, each tagged by the check as "too slow" or "fits".

Input

piles = [3, 6, 7, 11] h = 8
→

Answer space: speed → hours → fits?

k: 1 2 3 4 5 6 ... 11 hours: 27 15 10 8 8 6 ... 4 fits: no no no YES YES YES ... YES

Hours for one pile at speed k

(p + k - 1) // k, the ceiling of p / k: a pile of 7 at speed 3 takes 3 hours (3 + 3 + 1).

Hours for all piles

Add them up. At speed 4: 1 + 2 + 2 + 3 = 8. At speed 3: 1 + 2 + 3 + 4 = 10.

Fits or not

Compare with h = 8: speed 3 is too slow, speed 4 fits.

The line is sorted

A faster speed never needs more hours, so once "fits" appears it never turns back to "too slow". That ordering is all binary search needs.

Critical point: the bounds come from the problem, not from array indices. lo = 1 because speed 0 eats nothing (and divides by zero). hi = max(piles) because at that speed every pile takes exactly one hour, and h >= len(piles) is guaranteed.

Method 1: binary search the speed (Koko Eating Bananas)

The template, taken line for line from the notebook's hours_needed (docstring omitted) and min_eating_speed_binary. Each pass checks the middle speed, keeps it if it fits, and throws away the half that cannot contain the answer.

def hours_needed(piles: List[int], k: int) -> int: return sum((p + k - 1) // k for p in piles) # ceil(p / k) per pile, integers only def min_eating_speed_binary(piles: List[int], h: int) -> int: lo, hi = 1, max(piles) # bounds of the ANSWER (speeds), not of the array while lo < hi: # stop when one candidate is left mid = (lo + hi) // 2 if hours_needed(piles, mid) <= h: # feasible: mid works... hi = mid # ...so the answer is mid or smaller (keep mid) else: lo = mid + 1 # too slow: the answer is strictly bigger than mid return lo # lo == hi == smallest feasible speed

Key mental model

Each check answers "is the boundary to my left or right?" A fitting mid could still be the boundary, so it stays in the range; a failing mid cannot be, so it leaves with everything slower.

Common mistake

Writing hi = mid - 1 after a fit. At step 7 that would set hi = 3 and lose the answer 4, which only hi = mid keeps.

Why lower middle + lo = mid + 1

(lo + hi) // 2 rounds down, so mid < hi whenever lo < hi. Both branches then shrink the range, and the loop always ends.

Method 2: try every speed (the brute force it replaces)

The notebook's min_eating_speed_brute: walk the same yes/no line from the left, one speed at a time, and stop at the first "fits". It is correct, and it shows exactly what binary search saves: on this input it checks 4 speeds against binary search's 4, but in general it checks up to max(piles) speeds (up to 10^9), not about log2 of that.

def min_eating_speed_brute(piles: List[int], h: int) -> int: for k in range(1, max(piles) + 1): # every candidate speed, slowest first if hours_needed(piles, k) <= h: # first speed that fits in h hours... return k # ...is the minimum, since we go in increasing order return max(piles) # unreachable when h >= len(piles); kept for safety

Key mental model

This is a linear search for the first YES on a sorted yes/no line. Any time you see a linear search on something sorted, binary search is the upgrade.

Common mistake

Judging speed by this tiny example. The worst case is an answer near max(piles): with h = len(piles) the scan tries every single speed.

What the notebook measured

On piles = [1..n], h = n (answer = n): the scan grew about 4x per doubling (O(n·M) with M = n), binary search about 2.2x.

Edge cases you should test

Case A: h == len(piles)

piles = [30, 11, 23, 4, 20], h = 5

Answer = 30 (max(piles))

Every pile must be finished in a single hour, so the speed must be the biggest pile. This is why hi = max(piles) is always a safe upper bound.

Case B: far more hours than bananas

piles = [5, 5, 5], h = 1000

Answer = 1

Speed 1 already fits (15 hours). Every check succeeds, hi walks down to lo = 1. A search starting at lo = 0 would divide by zero here.

Case C: one huge pile

piles = [1000000000], h = 2

Answer = 500000000

Binary search needs about 30 checks. The brute force would need 500 million; the notebook skips it on this test for that reason.

Case D: smallest input

piles = [1], h = 1

Answer = 1

lo = hi = 1 from the start, so the loop body never runs and lo is returned.

How to derive this in an interview

Reasoning path

"Return the minimum speed" means I am choosing a number, not finding an element.

Given a speed, I can check it in one pass: total hours with ceiling division.

Faster never takes longer, so the check is monotonic over speeds.

The answer is in [1, max(piles)]; binary search for the first speed that fits.

What to say out loud

  • "Brute force tries every speed from 1 up: O(n·M), too slow with piles up to 10^9."
  • "If Koko finishes at speed k, she finishes at any faster speed, so I can binary search the speed."
  • "If mid fits, the answer is mid or smaller, so hi = mid; otherwise lo = mid + 1."
  • "About log2(M) checks, each O(n): O(n log M) time, O(1) space."

Common beginner coding mistakes

The binary search

  • hi = mid - 1 after a feasible mid: can skip the answer.
  • lo = mid with a lower middle: loops forever when hi = lo + 1.
  • Mixing templates: while lo <= hi with hi = mid never ends.
  • Searching indices of piles instead of speeds.

The feasibility check

  • Floor division p // k: undercounts hours for partial piles.
  • math.ceil(p / k): float rounding; use (p + k - 1) // k.
  • Starting at lo = 0: division by zero.
  • Upper bound too small (for example sum(piles) // h): may not be feasible.

Practice questions

This pattern has one NeetCode 150 problem, so questions 2 to 4 are follow-up variants: other LeetCode problems that reuse the same template with a different feasible. They are not in this folder; the README lists them with their search ranges.

Practice 1 — Koko Eating Bananas: piles = [30, 11, 23, 4, 20], h = 6

Hint: with 6 hours for 5 piles, exactly one pile may take two hours. Which pile should it be?

Answer: 23. At 23 the hours are 2 + 1 + 1 + 1 + 1 = 6. At 22 the pile of 23 also needs 2 hours: 7 in total, too slow. Step through the method on Koko Eating Bananas.

Practice 2 (variant) — Capacity To Ship Packages Within D Days (LC 1011): weights = [1..10], days = 5

Hint: the answer is a ship capacity in [max(weights), sum(weights)]. feasible(c): load packages in order, start a new day when the next one would go over c, and check the days used are at most 5.

Answer: 15. Capacity 15 gives [1..5] [6,7] [8] [9] [10] = 5 days; capacity 14 needs 6. Same loop as Koko; only bounds and check change.

Practice 3 (variant) — Split Array Largest Sum (LC 410): nums = [7, 2, 5, 10, 8], k = 2

Hint: guess the largest part sum x in [max(nums), sum(nums)]. feasible(x): greedily cut a new part when the running sum would exceed x; it fits if you used at most k parts. It is the shipping check with "days" renamed "parts".

Answer: 18, from [7, 2, 5] [10, 8]. "Minimize the largest" is the tell. Template: Koko Eating Bananas.

Practice 4 (variant) — Minimum Number of Days to Make m Bouquets (LC 1482): bloomDay = [1, 10, 3, 10, 2], m = 3, k = 1

Hint: guess a day d in [min(bloomDay), max(bloomDay)]. feasible(d): walk the flowers, count runs of k adjacent ones with bloomDay[i] <= d, and check you get at least m bouquets. If m * k > n, return -1 before searching.

Answer: 3. By day 3 the flowers blooming on days 1, 3 and 2 are open: 3 bouquets. With k = 2 instead, m * k = 6 > 5, so the answer is -1. See the template on Koko Eating Bananas.

Final takeaway

Search the answer, not the array. Find a range that surely holds the answer, write a monotonic yes/no check for one guess, and binary search for the first yes: feasible mid means hi = mid, otherwise lo = mid + 1. Koko's check is "total hours at this speed is at most h"; the variants swap in a different check and keep the loop.
