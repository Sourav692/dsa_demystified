981 · Time Based Key-Value Store

A dictionary that remembers every value a key ever had, and when.

The problem, in plain words

Build a store with two actions. set(key, value, time) saves a value for a key at a moment in time. get(key, time) asks: "what was this key's value at that moment?" That is the value saved most recently at or before the given time. If nothing was saved yet by then, answer "" (empty text).

Like a shop's price board: if the price changed at 1 pm and at 4 pm, then "what was the price at 3 pm?" is the 1 pm price.
Promise from the problem: the times passed to set only ever go up. So each key's history is automatically sorted by time.

This is LeetCode's example, replayed one call at a time. Each box is one saved entry: the time on top, the value underneath.

Both solutions store data the same way: a dictionary from key to a list of (time, value) pairs, appended by set in O(1). They differ only in get. The demos below run get("k", 12) on a key with six entries.

Solution 1 — Brute force: read the whole history on every get

Walk the key's list from the oldest entry to the newest. Whenever an entry's time is <= t, remember its value; a later one overwrites an earlier one. At the end, the remembered value is the answer.

res (best value so far)

Speed & memory: every get reads all n entries of the key — O(n) per get, O(1) extra memory. Measured: about 2× per doubling of the history.

Solution 2 — The smart way: binary search the history for the last time <= t

The history is sorted by time, so binary search it. Look at the middle entry. If its time is <= t, it is a valid answer: remember it, then look to the right for a later one that also fits (lo = mid + 1). If its time is too late, look left (hi = mid - 1). When the range is empty, the last remembered value is the answer.

res (best value so far)

Speed & memory: each look halves the range — O(log n) per get, O(1) extra memory; set stays O(1). Measured: about 1× per doubling.

When you'd use this

See "value at time t", "most recent version at or before", or "latest entry <= x" on data that arrives in order? Keep a sorted list per key and binary search for the last entry that fits, remembering each candidate as you go.
