A sorted list of numbers and one number to find. Where is it?

The problem, in plain words

You get numbers already sorted from smallest to largest, and a target number. Return the target's position (index, counting from 0). If it is not in the list, return -1. The catch: you must be fast, about log n steps, so reading every number is not allowed.

Think of a dictionary: to find "mango" you open the middle, see "kiwi", and know "mango" is in the second half. You never read page by page.

Same list, two targets: one that is there (9) and one that is not (2).

Solution 1 — Brute force: read every number

Start at the left and check each number in turn. Stop when you find the target. If you reach the end, it is not there. This works on any list, sorted or not, because it never uses the order.

Speed & memory: a missing target means reading all n numbers — O(n) time, O(1) memory. Measured in the notebook: about 2× slower each time the list doubles.

Solution 2 — The smart way: binary search (lo / hi / mid)

Keep two markers, lo and hi: the target, if it exists, is somewhere between them. Look at the middle one, mid. Too small? Everything up to mid is too small as well, so move lo to mid + 1. Too big? Move hi to mid - 1. Each look throws away half of what is left.

Speed & memory: every look halves the range, so about log₂ n looks — O(log n) time, O(1) memory. A million numbers need about 20 looks.

When the target is missing

Same loop, target 2. Watch lo and hi close in until they cross. Once lo > hi nothing is left to search, so the answer is -1.

When you'd use this

See "sorted" plus "find", or a required speed of O(log n)? Keep a [lo, hi] range, look at the middle, and throw away the half that cannot hold the answer.
