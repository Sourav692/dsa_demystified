Sorted Search

Find a value, or the boundary next to it, in data that is already sorted. Keep a range [lo, hi] that must contain the answer if there is one, compare the target with the middle element, and drop the half that cannot hold it. Every comparison halves the work, so a million items need about 20 looks.

Core idea: one comparison rules out half Method 1: Binary Search (exact match) Method 2: Time Based Key-Value Store (last fit) Interactive traces synced to code

Problems in this pattern: Binary Search · Search a 2D Matrix · Time Based Key-Value Store · pattern notes (README)

Canonical example

Binary Search, nums = [-1, 0, 3, 5, 9, 12], target = 9

Answer = 4 (two looks instead of five)

Why this pattern matters

Lookups in sorted data

Sorted IDs, sorted prices, a sorted log: binary search finds an entry in O(log n) without any extra index structure.

"As of" queries

Config versions, stock prices, document history: "what was the value at time t?" is the last entry at or before t in a time-sorted list.

The base of every binary search

Rotated arrays, search on the answer, and median of two arrays all reuse this loop. Get the range rules right here and they carry over.

Instructor note: binary search is short but easy to get subtly wrong. Learn one loop shape with one invariant ("the answer, if any, is inside [lo, hi]") and use it everywhere, instead of tweaking < versus <= until the tests pass.

What is sorted search?

Simple definition

Sorted search is binary search on data that is already in order. Compare the target with the middle element of the current range. Because everything left of it is smaller and everything right of it is larger, that one comparison proves which half cannot contain the answer. Drop that half, including the middle itself, and repeat until the answer is found or the range is empty.

The tell in a problem statement

The input is sorted ("ascending order", "each row is sorted", "timestamps are strictly increasing"), the task is to find something, and the required speed is O(log n). Boundary wording such as "largest timestamp <= t" or "most recent at or before" is the same pattern in its boundary form.

Beginner shortcut: the data does not have to be one flat list. A grid read row by row, or one key's history in a hash map, is a sorted list in disguise. Find the reading order in which it is sorted, then binary search the positions.

Step-by-step thinking process

1

Find the sorted order

A list, a grid read row by row, or a per-key history. If nothing is sorted, this is not the pattern.

2

Set the range

lo, hi = 0, len - 1: both ends included. The answer, if any, is inside.

3

Compare the middle

while lo <= hi: look at mid, then move lo = mid + 1 or hi = mid - 1.

4

Decide the exit

Exact match: return at the hit, -1 when empty. Boundary: record each fit, return the last one.

How the input becomes a search range

Binary search never works on "the data" directly. It works on a range of positions [lo, hi] plus a way to read the value at any position in O(1). Each problem in this pattern just has a different way to read position i.

Input

nums = [-1, 0, 3, 5, 9, 12] matrix = [[1, 3, 5, 7], [10, 11, 16, 20], [23, 30, 34, 60]] store = {"k": [(1,"a"), (4,"b"), (7,"c"), (10,"d"), (13,"e"), (18,"f")]}
→

Search range and "read position i"

positions 0..5 read nums[i] positions 0..11 r, c = divmod(i, 4) read matrix[r][c] positions 0..5 read store["k"][i][0] (the time of entry i)

Plain sorted list

Position i is just nums[i]. Range [0, len(nums) - 1].

Grid whose rows chain

Read row by row, the 12 cells are one sorted list. Position i lives at row i // 4, column i % 4 (4 = number of columns). Range [0, m·n - 1]; the flat list is never built.

Per-key history

set appends (time, value) and times only increase, so each key's list is sorted by time for free. Position i is the time of entry i.

Critical point: the loop below is the same for all three. Only the line that reads the value at mid changes, plus, for the history, what happens when there is no exact match.

Method 1: classic lo / hi / mid (Binary Search)

The template itself, line for line from the notebook's search_binary. The range starts as the whole array. Each pass computes mid, returns on a hit, and otherwise moves one end past mid. Traced on nums = [-1, 0, 3, 5, 9, 12], target = 9.

def search_binary(nums: List[int], target: int) -> int: lo, hi = 0, len(nums) - 1 # search space = the whole array, both ends inclusive while lo <= hi: # space [lo, hi] still holds at least one element mid = lo + (hi - lo) // 2 # middle index (this form never overflows in fixed-width languages) if nums[mid] == target: return mid if nums[mid] < target: lo = mid + 1 # mid and everything left of it are too small else: hi = mid - 1 # mid and everything right of it are too big return -1 # space is empty: target is not in nums

Key mental model

The range [lo, hi] is a promise: "if 9 is here at all, it is between these two." Step 2 keeps the promise because 3 < 9 and the array is sorted, so indices 0 to 2 are all too small.

Common mistake

Writing lo = mid instead of lo = mid + 1. mid was already checked; keeping it means a two-element range can pick the same mid forever.

Why sorted order matters

The comparison at mid says something about every element on one side only because the array is sorted. On unsorted data the dropped half could still hold the target.

Method 2: boundary form, last time <= t (Time Based Key-Value Store)

Here there is usually no exact hit to stop on: get("k", 12) wants the entry with the largest time that is still <= 12. Same loop, one change. When values[mid] fits, it might be the answer, so record it in res and keep looking to the right for a later fit. Code from the notebook's TimeMap.get, traced on the history (1,"a") (4,"b") (7,"c") (10,"d") (13,"e") (18,"f").

def get(self, key: str, timestamp: int) -> str: values = self.store.get(key, []) res = "" # answer if no entry has time <= timestamp lo, hi = 0, len(values) - 1 while lo <= hi: mid = (lo + hi) // 2 if values[mid][0] <= timestamp: res = values[mid][1] # valid candidate; a later one may also fit... lo = mid + 1 # ...so keep searching to the right else: hi = mid - 1 # too late: the answer is to the left return res

Key mental model

Every recorded res is a correct-but-maybe-not-latest answer. Moving lo right only ever finds a later fit, so the final res is the latest one. At the end, hi = 3 points at it and lo = 4 is one past it.

Common mistake

Returning at step 2, the first time a fit is seen. (7, "c") fits, but (10, "d") is later and also fits. The boundary form must keep searching.

Why the hash map

The dictionary sends get("k", ...) straight to k's own history in O(1), so the binary search covers only that key's n entries: O(log n) per get.

Edge cases you should test

Case A: the target is not there

nums = [-1, 0, 3, 5, 9, 12], target = 2

Binary Search = -1

Ranges: [0, 5] mid 2 (3 > 2, hi = 1), [0, 1] mid 0 (-1 < 2, lo = 1), [1, 1] mid 1 (0 < 2, lo = 2). Now lo = 2 > hi = 1: the range is empty, return -1.

Case B: one element

nums = [5], target = 5 and target = -5

0 and -1

lo = hi = 0. The <= in while lo <= hi is what lets this single element be checked at all; with < the loop would never run.

Case C: smaller or larger than everything

nums = [1, 3, 5, 7, 9, 11, 13], target = 0 and target = 14

-1 and -1

One end keeps moving until it crosses the other: hi falls to -1, or lo rises to 7. No index outside the array is ever read, because mid is only computed while lo <= hi.

Case D: get earlier than every stored time, or an unknown key

History [(10,"v1"), (20,"v2"), (30,"v3")], get("k", 9); and get("c", 10) for a key never set

"" and ""

No entry fits, so res keeps its starting value "". The unknown key gives an empty list (self.store.get(key, [])), so hi = -1 and the loop never runs.

Case E: a matrix with one row or one column

matrix = [[1, 3]] and matrix = [[1], [3]], target = 3

True and True

The flat search still works: with one column, divmod(i, 1) = (i, 0), so position i is row i. The index map must divide by the number of columns.

How to derive this in an interview

Reasoning path

The data is sorted (or sorted in some reading order) and I need to find something in it.

One comparison with the middle tells me which half cannot contain the answer, so I can drop half per step: O(log n).

I keep an inclusive range [lo, hi] with the invariant "the answer, if any, is inside", and always move past mid.

Exact match: return at the hit. "Last one that fits": record each fit and keep searching right.

What to say out loud

  • "The array is sorted, so I'll binary search: compare with the middle and discard the half that can't hold the target."
  • "My range is inclusive, lo = 0, hi = n - 1, loop while lo <= hi, and I move to mid + 1 or mid - 1 so it always shrinks."
  • "For the matrix, the rows chain, so it's one sorted list of m·n items; I map index i to divmod(i, n)."
  • "For the time map, each key's list is sorted by time because timestamps increase, so get is a binary search for the last time <= t: O(log n)."

Common beginner coding mistakes

Exact match (Binary Search, Search a 2D Matrix)

  • while lo < hi with hi = mid - 1: the last remaining element is never checked ([5], target 5 returns -1).
  • lo = mid or hi = mid in the inclusive form: the range can stop shrinking and loop forever.
  • hi = len(nums) together with <=: reads one past the end.
  • Mapping the flat index with the number of rows, divmod(mid, m), instead of columns.

Boundary form (Time Based Key-Value Store)

  • Returning at the first entry with time <= t instead of recording it and searching right.
  • Returning values[lo] after the loop: lo ends one past the answer.
  • Indexing self.store[key] on an unknown key with a defaultdict: it silently creates empty entries.
  • Sorting the history on every set: the times already arrive in order.

Practice questions

Practice 1 — Search a 2D Matrix: matrix = [[1,3,5,7],[10,11,16,20],[23,30,34,60]], target = 13

Hint: search positions 0 to 11 and read position i as matrix[i // 4][i % 4].

Answer: False. mid 5 is (1, 1) = 11 < 13, lo = 6; mid 8 is (2, 0) = 23 > 13, hi = 7; mid 6 is (1, 2) = 16 > 13, hi = 5; the range is empty. Step through all three approaches: Search a 2D Matrix.

Practice 2 — Time Based Key-Value Store: after set("foo","bar",1) and set("foo","bar2",4), what do get("foo",3) and get("foo",5) return?

Hint: for each query, find the last time in [1, 4] that is <= the query time.

Answer: "bar" (last time <= 3 is 1) and "bar2" (last time <= 5 is 4). This is LeetCode's example, replayed call by call on the Time Based Key-Value Store page.

Practice 3 — Binary Search: how many comparisons does search_binary make for target = 2 in [-1, 0, 3, 5, 9, 12], and why does it stop?

Hint: write down lo and hi after each comparison.

Answer: 3 comparisons (mid 2, then 0, then 1). After the third, lo = 2 > hi = 1, so the range is empty and it returns -1. Watch it on the Binary Search page.

Practice 4 — Follow-up variant of Binary Search (Search Insert Position): where would target = 2 be inserted to keep [-1, 0, 3, 5, 9, 12] sorted?

Hint: run the same loop as Practice 3 and look at lo when it ends.

Answer: index 2. When the exact-match loop ends without a hit, lo is the first index whose value is larger than the target, so returning lo instead of -1 solves this follow-up. Same trace as on the Binary Search page.

Practice 5 — Follow-up variant of Search a 2D Matrix (Search a 2D Matrix II): rows and columns are sorted, but a row may start below the previous row's end. Does the flat search still work?

Hint: is the row-by-row reading still one sorted list?

Answer: no. The flattened list is no longer sorted, so the flat binary search can drop the half that holds the target. The staircase walk from the top-right corner (O(m + n)) only needs sorted rows and columns, so it still works. It is Solution 2 on the Search a 2D Matrix page.

Final takeaway

Keep [lo, hi] around the answer, compare the middle, move past it. Binary Search uses the loop as is. Search a 2D Matrix changes only how position mid is read (divmod(mid, n)). Time Based Key-Value Store changes only the exit: record every fit and keep going right, because the answer is a boundary, not an exact hit.
