Rotated Array

Binary search on a sorted array that was cut at an unknown point and swapped around. The array is now two sorted runs. One extra comparison per step, nums[mid] against an endpoint, tells you which side of mid is still in order, and that is enough to throw away half the range every time.

Core idea: one side of mid is always sorted Method 1: Find Minimum (compare with nums[hi]) Method 2: Search (find the sorted half) Interactive traces synced to code

Why this pattern matters

Circular buffers and logs

A ring buffer of timestamps is sorted except where the write pointer wrapped around. Finding the oldest entry is finding the rotation point.

Binary search beyond "fully sorted"

Binary search does not need a sorted array; it needs a rule that says which half can hold the answer. Rotated arrays are the standard exercise in building that rule.

One idea, two problems

Find Minimum and Search share the same observation (one side of mid is sorted). Only the decision inside the loop changes.

Instructor note: plain binary search gives wrong answers here, and it fails silently. The whole pattern is one extra endpoint comparison per step that restores the order binary search depends on.

What is the rotated array pattern?

Simple definition

Take a sorted array of distinct values, cut it at some index, and move the front piece to the back: [0, 1, 2, 4, 5, 6, 7] becomes [4, 5, 6, 7, 0, 1, 2]. The result is two sorted runs, and every value in the first run is bigger than every value in the second. The point where the order restarts is the cliff, and the minimum sits right after it.

The tell in a problem statement

"Sorted array rotated at an unknown pivot", plus "must run in O(log n)". The question is either the minimum (where is the cliff?) or the index of a target value.

Beginner shortcut: cut the array at any mid and at least one side is a single sorted run. Compare nums[mid] with an endpoint to find out which. Inside a sorted run, "is the answer in here?" is just two comparisons.

Step-by-step thinking process

1

Spot "rotated" + O(log n)

Sorted, then rotated, with a log-time requirement: binary search, but the plain comparison is not trustworthy.

2

Pick the endpoint test

Minimum: nums[mid] > nums[hi]. Target: nums[lo] <= nums[mid] says the left half is sorted.

3

Decide the half

Minimum: cliff right of mid, or at/left of it. Target: inside the sorted half's range, or in the other half.

4

Pick the loop shape

Boundary (minimum): lo < hi, hi = mid. Value (target): lo <= hi, mid ± 1, return -1 at the end.

How the input becomes two sorted runs

The input is a plain list. Nothing is built from it: the "structure" is a fact about its values. Seeing the list as two runs separated by a cliff is what makes every comparison below meaningful.

Input list

nums = [4, 5, 6, 7, 0, 1, 2]
→

Two sorted runs

run 1 = [4, 5, 6, 7] indices 0..3 run 2 = [0, 1, 2] indices 4..6 every run-1 value > every run-2 value

Start sorted: [0, 1, 2, 4, 5, 6, 7]

One sorted run; the minimum is at index 0.

Rotate: move [0, 1, 2] to the back

The array becomes [4, 5, 6, 7, 0, 1, 2]: a big run, then a small run.

Read the right end

nums[hi] = 2 belongs to run 2. Any value bigger than it must be in run 1, so it lies left of the cliff.

Read any mid

If nums[lo] <= nums[mid], lo and mid are in the same run, so [lo..mid] is sorted. Otherwise the cliff is between them, and [mid..hi] is sorted.

Critical point: both problems in this folder have distinct values. That is what makes the endpoint comparison decisive. With duplicates, nums[mid] == nums[hi] can happen on either side of the cliff (see Practice 3).

Method 1: compare mid with the right end (Find Minimum in Rotated Sorted Array)

Code from the notebook's find_min_binary. If the middle value is bigger than the right end, mid is in the big run and the cliff is strictly to its right. Otherwise mid is in the small run, so the minimum is mid or something left of it: keep mid. The window shrinks until one index is left.

def find_min_binary(nums: List[int]) -> int: lo, hi = 0, len(nums) - 1 # search range while lo < hi: mid = (lo + hi) // 2 if nums[mid] > nums[hi]: # middle bigger than right end... lo = mid + 1 # ...the smallest must be to the RIGHT of mid else: hi = mid # smallest is at mid or to its LEFT return nums[lo] # lo == hi lands on the minimum

Key mental model

nums[hi] always belongs to the small run (or to the only run when there is no rotation). Bigger than it means "big run, cliff ahead"; not bigger means "small run, the minimum is here or behind".

Common mistake

Writing hi = mid - 1. At step 3, mid = 4 is the minimum; hi = 3 would throw it away.

Why compare with the right end

On an unrotated array like [11, 13, 15, 17], every mid is <= nums[hi], so hi walks down to index 0. A rule built on nums[lo] has no such guarantee.

Method 2: find the sorted half first (Search in Rotated Sorted Array)

Code from the notebook's search_rotated_binary, traced on the same array with target = 0. After the equality check, decide which half is sorted with nums[lo] <= nums[mid]. If the target falls in that sorted half's value range, go there; otherwise it can only be in the other half.

def search_rotated_binary(nums: List[int], target: int) -> int: lo, hi = 0, len(nums) - 1 while lo <= hi: mid = (lo + hi) // 2 if nums[mid] == target: return mid # found it if nums[lo] <= nums[mid]: # the LEFT half [lo..mid] is sorted if nums[lo] <= target < nums[mid]: hi = mid - 1 # target lies in that sorted left half else: lo = mid + 1 # otherwise it's in the right half else: # the RIGHT half [mid..hi] is sorted if nums[mid] < target <= nums[hi]: lo = mid + 1 # target lies in that sorted right half else: hi = mid - 1 # otherwise it's in the left half return -1

Key mental model

You can only trust a range check on a sorted piece. So first find the sorted half, ask "is the target between its ends?", and let a "no" send you to the other half without checking it.

Common mistake

Plain binary search (if nums[mid] < target: lo = mid + 1). At step 1 it sees 7 > 0 and goes left, away from 0, and returns -1.

Why <= in nums[lo] <= nums[mid]

When lo == mid (two elements left), the left half is one element, which is sorted. With < the code would wrongly treat the right half as the sorted one.

Edge cases you should test

Case A: rotated by zero

nums = [11, 13, 15, 17]

Find Minimum = 11

13 <= 17 gives hi = 1, then 11 <= 13 gives hi = 0. Comparing with the right end handles "not rotated at all" with no special case.

Case B: two elements, cliff in between

nums = [2, 1]

Find Minimum = 1

mid = 0, 2 > 1, so lo = 1 and the loop ends with lo == hi == 1.

Case C: the target is not in the array

nums = [4, 5, 6, 7, 0, 1, 2], target = 3

Search = -1

Probes mid = 3, 5, 6; each time the target falls outside the sorted half, then lo = 7 > hi = 6 ends the loop. A single element [1] with target = 0 also returns -1 after one probe.

Case D: the right half is the sorted one

nums = [5, 1, 3], target = 5

Search = 0

mid = 1: nums[lo] = 5 > nums[mid] = 1, so [1, 3] is the sorted half. 5 is not in (1, 3], so hi = 0, and the next probe finds it.

How to derive this in an interview

Reasoning path

"O(log n)" on an array means binary search, but rotation breaks the usual nums[mid] < target rule.

The array is two sorted runs. Any cut at mid leaves at least one side as a single sorted run.

An endpoint comparison identifies that side: nums[mid] > nums[hi] (minimum) or nums[lo] <= nums[mid] (target).

Decide the half from that, choose the loop shape (boundary or value), and check the edge cases: no rotation, two elements, absent target.

What to say out loud

  • "The array is sorted then rotated, so it's two sorted runs and one side of any midpoint is sorted."
  • "For the minimum I compare nums[mid] with nums[hi]: bigger means the cliff is to the right, otherwise mid might be the answer, so hi = mid."
  • "For a target I first find the sorted half, check whether the target is in its range, and keep that half or the other."
  • "Each step halves the range: O(log n) time, O(1) space. Values are distinct; duplicates would push the worst case to O(n)."

Common beginner coding mistakes

Find Minimum

  • hi = mid - 1, which can skip the minimum when mid is the minimum.
  • Comparing with nums[lo], which breaks on an unrotated array.
  • Looping on lo <= hi with hi = mid: when lo == hi, nothing changes and the loop never ends.
  • Returning lo (the index) when the problem asks for the value nums[lo].

Search

  • Plain binary search, ignoring the rotation.
  • nums[lo] < nums[mid] instead of <=, which misjudges the one-element left half.
  • Closed range check target <= nums[mid]: harmless after the equality check, but hides what the check is for. The notebook uses half-open ranges.
  • Range-checking the half that is not sorted; its ends say nothing about what lies between them.

Practice questions

Practice 1 — Find Minimum in Rotated Sorted Array: nums = [3, 4, 5, 1, 2]

Hint: the first mid is index 2. Compare nums[2] with nums[4].

Answer: 1. 5 > 2 gives lo = 3; then mid = 3, 1 <= 2 gives hi = 3, and lo == hi. Two probes. Step through it: Find Minimum in Rotated Sorted Array.

Practice 2 — Search in Rotated Sorted Array: nums = [4, 5, 6, 7, 0, 1, 2], target = 3

Hint: at each probe, name the sorted half and ask whether 3 is between its ends.

Answer: -1. Probes at mid = 3 (left [4..7] sorted, 3 not in it), mid = 5 (left [0..1] sorted, 3 not in it), mid = 6 (one element, 2 != 3), then the range is empty. See Search in Rotated Sorted Array.

Practice 3 — Follow-up variant (LeetCode 154, duplicates allowed): what does find_min_binary return for [1, 1, 1, 1, 0, 1, 1]?

Hint: at the first probe, nums[3] == nums[6]. Which branch runs, and which half does it drop?

Answer: it returns 1, which is wrong. The tie sends it to hi = mid = 3, dropping the 0 at index 4. This is a variant, not one of this pattern's problems: the usual fix adds a tie case, elif nums[mid] == nums[hi]: hi -= 1, which is safe because nums[hi] has a copy at mid. It costs the log-time guarantee: an all-equal array takes O(n) steps. The base version is on the Find Minimum page.

Practice 4 — Why does Find Minimum loop on lo < hi while Search loops on lo <= hi?

Hint: which loop keeps mid in the range, and which one throws it away?

Answer: Find Minimum searches for a boundary and keeps mid (hi = mid), so the range never empties; it stops at one candidate, which must be the answer. Search looks for a value and drops mid after checking it (mid ± 1), so it needs lo <= hi to check the last element and an empty range to mean "absent". Compare both on the Search page.

Final takeaway

One side of mid is always sorted; one endpoint comparison tells you which. Find Minimum compares nums[mid] with nums[hi] and converges on the cliff. Search finds the sorted half, range-checks the target against it, and keeps the half that can hold it. Same observation, two loop shapes, both O(log n).
