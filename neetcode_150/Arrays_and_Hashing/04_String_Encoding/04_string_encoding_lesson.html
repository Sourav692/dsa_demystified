String Encoding

Pack a list of strings into one string and get the exact list back. The trick: write each string's length, a # marker, then the content. The decoder reads the number, then takes exactly that many characters without looking at them, so the strings may contain any character at all, including #.

Core idea: length prefix, then content Method 1: Length-prefix encode / decode Method 2: Delimiter only (and why it breaks) Interactive traces synced to code

Problem in this pattern: Encode and Decode Strings (LeetCode Premium, free on neetcode.io) · pattern notes (README)

Canonical example

Encode and Decode Strings, strs = ["lint", "code", "a#b"]

decode(encode(strs)) = ["lint", "code", "a#b"]

Why this pattern matters

Network protocols

HTTP chunked transfer writes each chunk's size before the chunk. Redis sends a string as $5\r\nhello\r\n: length first, then the bytes. The receiver never guesses where a message ends.

File and wire formats

Binary formats such as Protocol Buffers store variable-length fields as "length, then bytes", so a field may hold any byte value without escaping.

The interview point

The question checks whether you notice that a separator is ambiguous when the data can contain it, and whether you can design a format that is not.

Instructor note: the whole problem is one design decision. Once you say "length first", the code is a dozen lines of slicing.

What is length-prefix encoding?

Simple definition

Each string becomes a frame: its length written in digits, a # that marks where the digits stop, then the string itself. "lint" becomes "4#lint". All frames are glued together. To decode, read the digits, then take exactly that many characters.

The tell in a problem statement

"Encode a list of strings to a single string", "serialize / deserialize", "send over the network", and above all: the strings may contain any character, so no separator is safe. decode receives only the encoded string.

Beginner shortcut: the decoder only ever looks for # at the start of a frame, where digits are guaranteed. After reading the length it jumps over the content in one slice, so a # inside the content is never examined.

Step-by-step thinking process

1

Try a separator

"#".join looks fine until a string contains #. Then ["a#b"] and ["a", "b"] encode the same.

2

Say the size first

If the reader knows a string has 3 characters, it does not care what they are. Write len(w) before each string.

3

End the number

Lengths can have several digits and content can start with a digit, so put a # after the length to say "the number stops here".

4

Decode frame by frame

From index i: scan to #, parse the length, slice the content, set i to the next frame. Stop at the end.

How the list becomes one framed string

The input is a Python list of strings. encode turns each one into a frame and joins them; the result is a single string where frame boundaries are known only from the lengths. That string is all decode ever sees.

Input list

strs = ["lint", "code", "a#b"]
→

Framed string (17 characters)

"4#lint" + "4#code" + "3#a#b" = "4#lint4#code3#a#b"

"lint" has 4 characters

Frame "4#lint" occupies indices 0 to 5. The header is indices 0 and 1.

"code" has 4 characters

Frame "4#code" occupies indices 6 to 11.

"a#b" has 3 characters

Frame "3#a#b" occupies indices 12 to 16. Its content contains a # at index 15.

Join once

"".join(parts) builds the 17-character result in one pass.

Critical point: the string has four # characters (indices 1, 7, 13, 15) but only three are markers. Nothing in the string itself says which; only the lengths do. That is why decode must read frames in order from the start.

Method 1: length-prefix encode and decode

The template itself, line for line from the notebook's encode and decode. Encode builds one frame per string. Decode keeps i at the start of a frame: j walks the digits to the #, the digits give length, and one slice takes the content.

def encode(strs: List[str]) -> str: parts = [] for w in strs: # Write "<length>#<content>" so the reader knows exactly how far to read. parts.append(str(len(w)) + "#" + w) return "".join(parts) # concatenate all the framed chunks def decode(s: str) -> List[str]: res = [] i = 0 while i < len(s): # keep reading chunks until the string ends j = i while s[j] != "#": # read digits up to the '#' marker j += 1 length = int(s[i:j]) # those digits are the content length start = j + 1 # content begins right after the '#' res.append(s[start:start + length])# take exactly `length` characters (any char is safe) i = start + length # jump to the start of the next chunk return res

Key mental model

A frame is a parcel with its weight written on the label. You read the label, lift exactly that much, and the next label is right behind it. You never open the parcel to look for the end.

Common mistake

Reading only one digit for the length. A 12-character string encodes as "12#..."; reading just "1" would take one character and lose the frame. The while s[j] != "#" loop reads every digit.

Why the marker is needed

Without #, "12abc" could be length 1 with content "2", or length 12. The marker says where the number stops, even when the content starts with a digit (the notebook tests "3#weird", which encodes as "7#3#weird").

Method 2: delimiter only (the brute idea it replaces)

The first idea most people try, from the notebook's encode_naive / decode_naive: join with # and split on #. It costs the same O(total length), but it gives the wrong answer as soon as a string contains #. Traced on the same input.

def encode_naive(strs: List[str]) -> str: # Join with a '#'. UNSAFE: breaks if any string itself contains '#'. return "#".join(strs) def decode_naive(s: str) -> List[str]: # Splitting on '#' can't tell a real '#' apart from a separator. return s.split("#") if s != "" else []

Key mental model

A separator is information mixed into the data stream. If the data can contain the same symbol, the stream no longer says which is which.

Common mistake

Picking a "rare" separator such as a Unicode symbol or "|#|". The constraint says any character may appear, so a rare separator only makes the bug rarer, not gone.

A second failure

[] and [""] both encode to "", so the naive decoder must guess. It returns [], which is wrong for [""]. Length prefix gives "" and "0#".

Edge cases you should test

Case A: no strings at all

strs = []

encode = "" · decode("") = []

while i < len(s) is false immediately, so decode returns an empty list. The notebook's correctness check includes this case.

Case B: empty strings

strs = ["", "", ""] and strs = [""]

"0#0#0#" → ["", "", ""] · "0#" → [""]

A length of 0 gives the slice s[start:start], the empty string, and i moves just past the marker. Every empty string still leaves a visible "0#", so [""] and [] stay different.

Case C: the data contains the marker

strs = ["a#b", "3#weird", "we#ird"]

"3#a#b7#3#weird6#we#ird" → ["a#b", "3#weird", "we#ird"]

This is the notebook's tricky test. "3#weird" even looks like a frame header inside the content, and it is still skipped, because decode jumps over content by its length.

Case D: a length with two digits

strs = ["abcdefghijkl"] (12 characters)

"12#abcdefghijkl" → ["abcdefghijkl"]

j walks over both digits 1 and 2 before it reaches #, so int(s[i:j]) is 12, not 1.

How to derive this in an interview

Reasoning path

Strings may contain any character, and decode sees only the encoded string.

So any separator can also be data: ["a#b"] and ["a", "b"] collide.

Instead of marking where a string ends, say up front how long it is.

Lengths have variable digit counts, so end the number with #. Only the first # after a frame start is a marker.

What to say out loud

  • "A delimiter alone is ambiguous because the data can contain it, so I'll prefix each string with its length."
  • "Each frame is length, #, content. The # ends the digits, so multi-digit lengths work."
  • "Decode reads digits up to #, slices exactly that many characters, and jumps to the next frame. A # in the content is never searched."
  • "Both directions touch each character once: O(total length) time and space."

Common beginner coding mistakes

Length-prefix (Method 1)

  • Reading a single digit for the length, which breaks on strings of 10 or more characters.
  • Starting the # search from index 0 or using s.index("#") on the whole string, which finds markers inside content.
  • Off by one after the marker: content starts at j + 1, and the next frame at start + length.
  • Building the result with += in a loop instead of collecting parts and calling "".join once.

Delimiter only (Method 2)

  • Assuming the delimiter never appears in the data, when the problem says any character can.
  • Choosing a longer or rarer delimiter and calling it fixed.
  • Missing that [] and [""] encode to the same empty string.
  • Escaping only # but not the escape character itself, so "/" followed by # becomes ambiguous.

Practice questions

This pattern has one NeetCode problem, so Practice 2 to 4 are follow-up variants of Encode and Decode Strings, the kind an interviewer asks next. Commit to a guess before opening the answer.

Practice 1 — Encode and Decode Strings: decode "3#abc0#2#ab" by hand

Hint: read digits to the #, take that many characters, repeat from where you stopped.

Answer: ["abc", "", "ab"]. The middle frame "0#" is an empty string. Step through the decoder on the problem page: Encode and Decode Strings.

Practice 2 — Variant: find two different lists that the delimiter-only scheme encodes to the same string

Hint: put the delimiter inside one string, or use empty strings.

Answer: ["a#b"] and ["a", "b"] both give "a#b"; [] and [""] both give "". Once two inputs share an encoding, no decoder can be right for both. Length prefix gives "3#a#b" vs "1#a1#b", and "" vs "0#". See the naive approach in the notebook: encode_and_decode_strings.ipynb.

Practice 3 — Variant: make the delimiter scheme correct with escaping instead of lengths

Hint: pick an escape character, say /. Escape both / and # inside the data, then end every string with a plain #.

Answer: encode each string as w.replace("/", "//").replace("#", "/#") + "#". Decode walks character by character: / means "the next character is literal data", a plain # ends the current string. ["lint", "code", "a#b"] becomes "lint#code#a/#b#". It is also O(total), but decode must look at every character, while the length prefix slices content without reading it. Compare with the length-prefix decoder on the problem page.

Practice 4 — Variant: drop the # by using a fixed-width length header

Hint: if every length is written with exactly 4 digits, how does the decoder know where the number stops?

Answer: write f"{len(w):04d}" + w, so "lint" becomes "0004lint". Decode reads int(s[i:i+4]), takes that many characters, and sets i += 4 + length. No marker is needed because the header width is fixed. The cost is a cap: 4 digits allow lengths up to 9999, which covers LeetCode's limit of 200. Real binary protocols do the same with a fixed number of bytes. Back to the pattern notes.

Final takeaway

Say the length first, then the content. A separator can always be confused with data; a length cannot, because the decoder never reads the content to find its end. Frame each string as len + "#" + content, decode by reading digits to the # and slicing exactly that many characters, and the round trip is exact for any characters in O(total length).
